# 智能客服 Agent —— 需求文档

## 1. 项目概述

本项目构建一个面向电商售后场景的智能客服 Agent，基于企业知识库回答用户关于产品/服务的问题，支持多轮对话与模糊问题澄清，能够识别用户意图（问答 / 投诉 / 咨询），并在无法回答时自动生成工单转接人工客服。

## 2. 术语与范围

| 术语 | 说明 |
| ---- | ---- |
| 知识库问答（RAG） | 基于知识库文档检索 + 生成模型回答产品/服务相关问题 |
| 意图识别 | 将用户消息分类为「问答」「投诉」「咨询」「模糊」四类之一 |
| 多轮对话 | 同一会话内保留上下文，支持追问与澄清 |
| 澄清 | 当用户问题过于模糊时，主动向用户提出澄清问题 |
| 工单转人工 | 无法回答或需人工介入时，生成工单交由人工客服 |
| 分库分索引 | 将知识库按文档拆成多个子索引，检索时先路由到相关分片再召回 |
| 多跳问题 | 需结合多个知识片段才能回答的问题 |
| ReAct | 推理（Reasoning）+ 行动（Acting）循环，LLM 多轮思考决定检索 / 回答 / 澄清 / 转人工 |
| 可观测性 / 监控大盘 | 采集请求运行指标并可视化展示（意图 / 延迟 / 来源 / 工单等），用于状态监控 |

## 3. 功能需求

### FR-1 基于知识库回答产品/服务问题

- 系统内置至少 10 份电商售后知识文档（配送、退换货、退款、发票、会员积分、支付安全、故障排查、隐私政策、投诉渠道、大促活动、客服联系方式等）。
- 用户提问后，系统通过检索增强生成（RAG）从知识库召回相关内容并生成回答。
- 检索采用混合打分：语义向量余弦 + 查询词面覆盖；语义向量优先使用本地中文向量模型（bge），未安装时自动回退离线哈希嵌入。
- 支持多跳问题：需结合多个知识片段才能回答的问题，自动拆分多个子查询分别检索后综合回答。
- 回答需基于知识库内容，不得凭空编造（未命中时明确表示无法回答）。

### FR-2 多轮对话与澄清

- 同一会话（session）内保留历史上下文。
- 当用户问题过短、语义模糊无法确定意图时，系统主动澄清并引导用户补充信息。

### FR-3 意图识别

识别用户意图为以下四类之一：

| 意图 | 说明 | 示例 |
| ---- | ---- | ---- |
| 问答（qa） | 售后/使用/操作类具体问题 | 「退款多久到账」「怎么申请退货」 |
| 咨询（consultation） | 售前/政策/服务咨询 | 「支持分期付款吗」「会员怎么开通」 |
| 投诉（complaint） | 不满 / 投诉 / 举报 | 「你们服务太差了，我要投诉」 |
| 模糊（unclear） | 过短或语义不明，需澄清 | 「这个」「有问题」 |

### FR-4 工单转人工

- 以下两类场景生成工单并转人工：
  1. **投诉类**：用户表达不满或投诉，直接登记工单，由人工客服跟进；
  2. **无法回答**：知识库检索置信度低于阈值（知识库未覆盖），生成工单转人工。
- 工单需包含：工单号、意图、用户原始消息、摘要、状态、创建时间。

### FR-5 用户历史对话

- 系统持久化每个会话（session）的对话记录（用户消息与客服回复），服务重启后不丢失。
- 用户在同一会话继续对话时，系统自动加载该会话的历史上下文，支持跨轮次追问。
- 提供会话历史查询接口：列出全部会话、查看某个会话的完整对话记录。

### FR-6 用户长期记忆

- 系统按用户（user_id）持久化其历史问答（长期记忆），跨会话、跨时间生效，服务重启不丢。
- 用户换新会话（不同 session_id）继续提问时，系统自动加载该用户近期记忆并注入回答上下文，实现「跨对话记住之前的回答」。
- 记忆按用户设置上限（如最近 50 条），以「用户曾问…当时回答…」的形式注入回答提示词；澄清话术不算有效回答，不写入记忆。
- 提供记忆查询接口：查看某用户的记忆记录。

### FR-7 分库分索引路由检索

- 知识库按文档拆分为多个分片（子索引），每个分片独立建向量索引。
- 检索时先由路由器（Router）按关键词把查询路由到相关分片，只在命中的分片上召回，缩小检索范围、降低无关文档噪声。
- 路由器未命中任何分片时回退全量检索，保证「无法回答 → 转人工」等既有行为不受影响。
- 多跳问题拆分出的每个子查询各自路由到对应分片，实现「路由 + 多跳」协同。

### FR-8 ReAct 多轮推理

- qa / consultation 类问题走有界 ReAct 循环（上限 `MAX_REACT_ROUNDS` 轮，默认 3）。
- 每轮由 LLM 决定下一步动作：检索（retrieve）、回答（answer）、澄清（clarify）或转人工（escalate）。
- 复杂 / 多跳问题可在多轮内拆分检索、追加上下文；超过上限轮次后强制收敛（有上下文则回答，否则转人工）。

### FR-9 可观测性与监控大盘

- 系统采集每轮对话的可观测指标：意图、响应延迟、检索来源、是否澄清、是否转人工。
- 提供监控大盘前端页面，实时展示：总请求数、会话数、工单数、平均延迟、意图分布、检索来源 Top、工单/延迟摘要、最近请求明细、系统信息（LLM 后端 / 向量后端 / 分片路由）。
- 大盘数据自动刷新；实时指标为内存实现（重启清零），会话 / 工单 / 记忆等持久化计数单独统计。

## 4. 非功能需求

| 编号 | 需求 | 说明 |
| ---- | ---- | ---- |
| NFR-1 | 可运行性 | 未配置任何 LLM API Key 时，以离线 Mock 模式可完整运行，测试与评测零成本可复现 |
| NFR-2 | 可插拔 | LLM 通过 OpenAI 兼容接口接入，可切换 DeepSeek / 通义 / 智谱 / OpenAI 等 |
| NFR-3 | 可测试性 | 核心逻辑（意图、检索、路由、工单、接口）具备自动化测试 |
| NFR-4 | 可评测 | 提供评测集与评测脚本，量化意图准确率、检索命中率、答案覆盖、转人工准确率 |
| NFR-5 | 可部署 | 通过 FastAPI 提供服务，接口规范清晰 |
| NFR-6 | 中文支持 | 知识库、回答、澄清均使用中文 |
| NFR-7 | 可观测性 | 提供 `/metrics` 指标接口与监控大盘前端，可观测请求量、意图分布、延迟、检索来源等运行指标 |

## 5. 用户故事

- 作为用户，我希望直接提问就能得到售后政策答案，而不是翻遍帮助中心。
- 作为用户，当我只说「退款」这种模糊话术时，希望客服能反问我要退款什么。
- 作为用户，当我投诉时，希望尽快有真人客服介入，而不是被机器人敷衍。
- 作为客服管理者，我希望机器人答不了的问题自动生成工单，而不是流失用户。

## 6. 验收标准

1. 知识库文档 ≥ 10 份，覆盖问答/咨询/投诉所需信息。
2. 意图识别准确率 ≥ 90%（离线评测集）。
3. 检索命中率（Hit@TopK）≥ 90%（离线评测集）。
4. 转人工准确率 ≥ 90%（该转人工时转、不该转时不转）。
5. 投诉与「无法回答」两类场景均能生成结构化工单。
6. 模糊问题能触发澄清。
7. FastAPI 接口可正常启动并响应 `/chat`、`/tickets`、`/sessions`、`/health`。
8. 会话历史可持久化（重启不丢），并能通过接口查询。
9. 跨会话记忆：同一用户换新会话后，系统仍能结合其历史问答作答。
10. 多跳问题能结合多个知识片段综合作答。
11. 检索能路由到相关分片（分库分索引），命中率不因分片而下降。
12. 监控大盘能展示请求 / 会话 / 工单 / 延迟等指标，并随请求实时更新。
