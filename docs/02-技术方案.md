# 智能客服 Agent —— 技术方案

## 1. 技术选型

| 关注点 | 选型 | 理由 |
| ---- | ---- | ---- |
| 流程编排 | LangGraph | 用状态图表达「意图分类 → 路由 → 处理」的多分支流程，自带 checkpointer 支持多轮 |
| 服务框架 | FastAPI + Uvicorn | 轻量、异步、自带 OpenAPI 文档 |
| LLM 接入 | OpenAI 兼容接口（`openai` SDK + `base_url`） | 一套代码适配 DeepSeek / 通义 / 智谱 / OpenAI 等 |
| 离线回退 | 确定性 Mock Provider | 无 Key 时测试/评测零成本可跑 |
| 向量计算 | NumPy 余弦 + 本地 sentence-transformers（bge-small-zh-v1.5） | 语义向量本地推理，无外部向量库/接口 |
| 分库分索引 | 关键词路由器（Router）+ 按文档分片建索引 | 缩小检索范围、降低无关噪声，确定性可离线测试 |
| 数据模型 | Pydantic v2 | 接口输入输出校验 |
| 测试 | pytest + FastAPI TestClient | 覆盖意图/RAG/图/工单/接口 |
| 可观测性 | 内存 `MetricsStore` + `/metrics` 接口 + 原生前端大盘 | 采集请求指标、可视化监控，无外部监控依赖 |

## 2. 总体架构

```
┌─────────────────────────────────────────────────────────┐
│                        FastAPI (api/main.py)             │
│        /chat  /tickets/{id}  /tickets  /health           │
└───────────────┬─────────────────────────────────────────┘
                │
┌───────────────▼─────────────────────────────────────────┐
│              LangGraph 编排 (agent/graph.py)             │
│   reset → 意图分类 → 路由 → 处理（RAG 回答/投诉工单/澄清/转人工）│
└───────┬──────────────────────────────┬──────────────────┘
        │                              │
┌───────▼────────┐              ┌──────▼──────────────┐
│  RAG (rag/)     │              │  LLM Provider (llm/) │
│ 加载/切块/嵌入/  │              │  classify/think/     │
│ 分片路由/混合检索│              │  answer/clarify/embed│
└────────────────┘              └─────────────────────┘
```

分层说明：

- **api 层**：接收请求、组织响应，不承载业务逻辑。
- **agent 层**：LangGraph 图 + 各意图处理节点 + 工单存储 + 可观测指标采集。
- **rag 层**：文档加载、分块、嵌入、混合检索，与 LLM 解耦。
- **llm 层**：LLM 能力抽象（意图分类 / 生成 / 澄清 / 嵌入），可插拔。

## 3. LangGraph 流程

```
START
  │
  ▼
classify_intent ── 输出意图：qa / consultation / complaint / unclear
  │
  ├── complaint ─────► handle_complaint ── 生成投诉工单 ──► END
  ├── unclear ───────► clarify ──────────── 生成澄清提问 ──► END
  └── qa/consultation► ReAct 循环（有界 ≤ MAX_REACT_ROUNDS 轮）
                          │
                          ▼
                     react_think ── LLM 决定下一步动作
                          │
        ┌─────────────────┼────────────────────┐
        ▼                 ▼                    ▼
     retrieve           answer            clarify / escalate
     （检索，追加上下文）（最终回答）        （澄清 / 转人工工单）
        │
        └────── 未达上限 → 回到 react_think ──┘（达上限：有上下文则强制回答，否则转人工）
```

关键设计点：

- **ReAct 循环（Reasoning + Acting）**：`qa`/`consultation` 走有界 ReAct。每轮 `provider.think()` 让 LLM 决定下一步 `answer` / `retrieve` / `clarify` / `escalate`，实现复杂问题的多轮检索与模糊问题的多轮澄清，超过上限轮次后强制收敛。
- **多跳问题分解**：`think()` 的 `retrieve` 动作的 `content` 可用换行/分号列出多个子检索词（如「退货的电器退款多久到账」拆成「退货」「退款」）。`retriever.search_many()` 对每个子查询并行召回、按 (source, content) 去重合并，一次性把跨文档的相关片段都注入上下文，再由 `answer()` 综合回答，避免串行多轮检索超上限。
- **意图路由**：`complaint` 直接转工单；`unclear` 走澄清；`qa`/`consultation` 走 ReAct。
- **转人工判定**：检索无命中（得分低于阈值）或 LLM 判定 `escalate` → 生成工单转人工。
- **多轮/历史**：图本身无状态（不依赖 checkpointer）。每次 `run(message, history, memory)` 由 API 层把持久化的会话历史与用户长期记忆显式传入，`messages` 即完整历史；跨服务重启也能保持上下文。

## 4. RAG 设计

### 4.1 流水线

```
知识库 .md 文档 ──加载──► 按标题分节 + 定长切块（重叠）──► 嵌入 ──► 按文档分片建 NumPy 向量矩阵
查询 ──路由(分片)──► 嵌入 ──► 余弦相似度 + 词面覆盖 ──► Top-K 召回 ──► 拼接上下文 ──► 生成回答
```

### 4.2 混合检索打分

```
score = 0.3 * cosine_norm + 0.7 * coverage
```

- `cosine_norm`：查询向量与文档块向量的余弦相似度，归一化到 [0,1]（真实 embedding 时的语义信号）。
- `coverage`：查询「内容 bigram」被文档块覆盖的比例（词面信号，稳健判别相关/无关）。
- 计算 bigram 前先剥离标点与停用字（的/了/是/怎么/请问/为什么…），避免语气词稀释内容词覆盖度。

### 4.3 嵌入

- 真实模式：本地 `sentence-transformers` + `BAAI/bge-small-zh-v1.5`（中文语义向量，512 维），由 `LocalEmbedder` 懒加载、失败自动回退。
- 离线模式：`hash_embed()` —— 基于内容 bigram 的 feature hashing，L2 归一化，确定性、无外部依赖。
- 聊天模型服务若不提供 embedding 接口，自动回退到 `hash_embed`。

### 4.4 分库分索引（路由器）

- 每个知识文档（`source`）= 一个分片（子索引），`Retriever.build()` 按 source 分片各自建独立向量矩阵。
- 检索时先用 `Router.route(query)` 按关键词把查询路由到相关分片（命中关键词越多越靠前，最多 `ROUTE_TOP_N` 个），只在这些分片上召回；无命中回退全量，保证转人工判定等既有行为不变。
- 多跳问题拆分出的每个子查询各自路由到对应分片，再由 `search_many()` 合并去重，实现「路由 + 多跳」协同。

## 5. LLM 接入层

抽象接口 `LLMProvider`（见 `cs_agent/llm/base.py`）：

| 方法 | 作用 |
| ---- | ---- |
| `classify_intent(history)` | 根据对话历史分类意图 |
| `think(question, context, memory, round)` | ReAct 思考：决定下一步 answer / retrieve / clarify / escalate |
| `answer(question, context, memory)` | 基于检索上下文生成回答（可结合用户长期记忆） |
| `clarify(question)` | 生成澄清提问 |
| `summarize_complaint(message)` | 投诉摘要（默认原样返回） |
| `embed(texts)` | 文本向量化 |

两个实现：

1. **OpenAICompatibleProvider**：`openai.OpenAI(api_key, base_url)`，通过 `chat.completions` 实现生成能力（意图分类 / ReAct 思考 / 回答 / 澄清）；embedding 优先本地 bge 模型，否则回退哈希嵌入（DeepSeek 不提供 embedding 接口）。
2. **MockProvider**：确定性规则实现（关键词分类 + 召回上下文直接作为回答），用于离线测试与评测。

工厂 `cs_agent/app.py::get_provider()`：`LLM_API_KEY` 为空 → Mock，否则 → OpenAI 兼容。

## 6. 数据模型（schemas.py）

- `Intent`：qa / consultation / complaint / unclear
- `Ticket`：id / intent / user_message / summary / status / created_at
- `ChatRequest` / `ChatResponse`：接口输入输出
- `RetrievedDoc`：source / content / score

## 7. FastAPI 接口

| 方法 | 路径 | 说明 |
| ---- | ---- | ---- |
| GET | `/health` | 健康检查（含当前 LLM 后端） |
| POST | `/chat` | `{message, session_id}` → `{reply, intent, needs_clarification, ticket, sources}` |
| GET | `/tickets` | 工单列表 |
| GET | `/tickets/{id}` | 单条工单 |
| GET | `/sessions` | 会话列表（按最近更新倒序） |
| GET | `/sessions/{id}` | 某会话的完整对话历史 |
| GET | `/memory/{user_id}` | 某用户的长期记忆 |
| GET | `/metrics` | 监控大盘聚合数据（系统信息 + 实时指标 + 持久化计数） |
| GET | `/dashboard` | 监控大盘前端页面 |

会话历史持久化：

- 由 `ConversationStore`（`cs_agent/agent/history.py`）按 `session_id` 将用户/客服消息写入 JSON 文件（`data/conversations.json`），服务重启不丢。
- `/chat` 每次先加载该会话历史、连同本轮消息显式传入无状态 LangGraph 图，处理完再把本轮问答写回。
- `/sessions` 与 `/sessions/{id}` 提供历史查询；`/chat` 的 `session_id` 即持久化键。

用户长期记忆（跨会话）：

- 由 `MemoryStore`（`cs_agent/agent/memory.py`）按 `user_id` 持久化历史问答，跨会话、重启不丢（`data/memory.json`，每用户最多保留 50 条）。
- `/chat` 每轮先加载该用户近期记忆、格式化为 `【用户历史记忆】` 注入回答提示词；回答后把本轮问答写回记忆（澄清话术除外）。
- `/memory/{user_id}` 提供记忆查询；前端用 `localStorage` 固定 `user_id`，因此「新会话」只换 session 而保留同一用户，记忆不断。

可观测性与监控大盘：

- 由 `MetricsStore`（`cs_agent/agent/metrics.py`）在 `/chat` 处理时采集：意图、响应延迟、检索来源、是否澄清、是否转人工，内存实现（线程安全，重启清零）。
- `/metrics` 聚合返回：系统信息（LLM 后端 / 模型 / 向量后端 / 分片路由 / 版本）+ 实时指标（请求数、意图分布、延迟 avg/max/min、检索来源 Top、最近 50 条请求）+ 持久化计数（会话 / 工单 / 记忆用户数 + 工单拆分）。
- `/dashboard` 返回监控大盘页面（`frontend/dashboard.html` + `dashboard.js` + `dashboard.css`），前端每 5 秒拉取 `/metrics` 刷新，展示 KPI 统计卡、意图分布、检索来源 Top、系统信息、工单 / 延迟摘要、最近请求表。

## 8. 评测方案（eval/）

评测集 `eval/eval_set.jsonl` 共 26 条，覆盖 4 类意图 + 多跳 + 转人工场景。脚本 `run_eval.py` 计算：

| 指标 | 定义 |
| ---- | ---- |
| 意图识别准确率 | 预测意图 == 期望意图 的比例 |
| 检索命中率 Hit@TopK | 期望文档出现在 Top-K 召回中的比例 |
| 答案关键信息覆盖 | 回答包含期望关键词的比例 |
| 转人工准确率 | 是否生成工单 与 期望 的一致比例 |

## 9. 测试方案（tests/）

- `test_intent.py`：意图分类规则正确性、嵌入确定性/归一化
- `test_rag.py`：检索器建库/召回/相关文档命中/无关查询低分/路由收窄分片
- `test_router.py`：分库分索引路由器（单分片/多跳多分片/无命中回退/top_n）
- `test_graph.py`：端到端路由（问答/咨询/投诉/澄清/转人工）、多跳、多轮历史、工单不串轮
- `test_ticket.py`：工单生命周期
- `test_api.py`：FastAPI 接口（TestClient）
- `test_metrics.py`：可观测指标记录/快照、`/metrics` 接口、监控大盘页面

## 10. 部署与运行

```bash
# 1) 创建虚拟环境并安装依赖
python -m venv .venv
.venv/Scripts/pip install -r requirements.txt   # Windows；Linux/Mac 用 .venv/bin/pip

# 2) 启动服务（未配置 Key 时自动离线 Mock）
.venv/Scripts/python -m uvicorn cs_agent.api.main:app --reload

# 3) 运行测试与评测
.venv/Scripts/python -m pytest
.venv/Scripts/python eval/run_eval.py
```

## 11. 配置项（.env / 环境变量）

| 变量 | 默认 | 说明 |
| ---- | ---- | ---- |
| `LLM_API_KEY` | 空 | 为空则离线 Mock |
| `LLM_BASE_URL` | `https://api.deepseek.com` | OpenAI 兼容端点 |
| `LLM_MODEL` | `deepseek-v4-pro` | 聊天模型 |
| `EMBED_BACKEND` | `local` | 向量后端：local=本地 bge；hash=离线哈希嵌入 |
| `LOCAL_EMBED_MODEL` | `BAAI/bge-small-zh-v1.5` | 本地 sentence-transformers 模型 |
| `EMBED_MODEL` | `text-embedding-3-small` | OpenAI 兼容端点的嵌入模型（DeepSeek 留空） |
| `TOP_K` | 3 | 召回条数 |
| `SCORE_THRESHOLD` | 0.25 | 转人工置信度阈值 |
| `CHUNK_SIZE` / `CHUNK_OVERLAP` | 400 / 50 | 分块参数 |
| `MAX_REACT_ROUNDS` | 3 | ReAct 循环最大轮次 |
| `ENABLE_ROUTING` | `1` | 是否启用分片路由器 |
| `ROUTE_TOP_N` | 3 | 路由器最多保留的分片数 |

## 12. 已知边界与后续优化

- 词面覆盖对「同一概念出现在多份文档」的场景（如「运费」同时存在于配送与退换货文档）存在歧义，已通过「本地 bge 语义向量 + 分库分索引路由」缓解；路由器为关键词规则式，对关键词未覆盖的隐式表述可升级为 LLM 语义路由。
- 工单存储为内存实现，生产环境可替换为数据库。
- 会话历史与用户长期记忆已持久化到本地 JSON 文件（`ConversationStore` / `MemoryStore`），图本身无状态；生产环境可替换为数据库或分布式 checkpointer。
